# Migrating to v0.45.2

`postgres.RunMigrations` no longer records a migration that failed, runs one runner at a time per
schema, and retries a migration that gave up waiting for a lock.

## Do I need to act?

**Recommended.** Give the connection your migrations job runs on a `lock_timeout`. Without one, a
migration that waits for a lock holds every query on its table behind it for as long as it waits.

**Check once, if a migration ever failed in production.** Earlier versions recorded a migration as
applied before running it, so one that failed stayed recorded without its changes, and every later
run skipped it. Compare `bun_migrations` with the schema the migration should have produced.

## Give the migrations connection a lock timeout

Set it on the options of the migrations job only, after any other connection parameters:
`pgdriver.WithConnParams` replaces the parameters set before it.

```go
var PostgresPresetMigrations = postgrespresets.NewDefault(append(connectionOptions,
	pgdriver.WithConnParams(map[string]any{"lock_timeout": "3s"}),
)...)
```

```go
// cmd/migrations
ctx := lo.Must(postgres.NewContext(context.Background(), config.PostgresPresetMigrations))
lo.Must0(postgres.RunMigrationsContext(ctx, migrations.Migrations))
```

A migration that waits longer than that for a lock now gives up, so the queries queued behind it
proceed. `RunMigrations` runs it again after two seconds, up to five times, before it fails the job.

## What changes on its own

- A migration is recorded once it succeeds. PostgreSQL runs a migration file as one transaction,
  so a failed one leaves nothing behind and the next run applies it. A file split with
  `--bun:split` is the exception: the parts before the failure stay applied.
- Runners against the same schema wait for each other, through a lock PostgreSQL releases when the
  runner's session ends, even when the runner dies. A runner keeps one connection of its pool for
  the wait, so the pool needs room for two.
