# Migrating to v0.25.0

Nothing to change. The release alters two defaults, and each deserves a deliberate
decision. Both were the standard library's behavior, leaking through presets that
otherwise make opinionated choices, and neither ever reported a problem.

## Idle database connections

`postgrespresets.Default` now keeps up to **ten** idle connections per pool. It
previously kept the `database/sql` default, which is **two**.

Past the second concurrent query, every call opened a fresh connection, paying a
TCP round trip, a TLS handshake and a PostgreSQL authentication exchange, then
discarded it on release. Nothing reported it, and it set a latency floor under
every query in every service.

### The capacity arithmetic, which is the reason to read this

The limit is **per process**. The sum across every replica, plus any job that
connects, has to stay under the database's `max_connections`:

```
replicas x idle_per_replica  +  jobs  <  max_connections
```

A stock PostgreSQL allows 100. Ten replicas of one service now hold 100 idle
connections on their own. A deployment that runs more replicas than that
arithmetic allows raises `max_connections` or lowers the pool.

### Overriding it

The field is on the config, so it is set where the config is built:

```go
config := postgrespresets.NewDefault(pgdriver.WithDSN(dsn))
config.MaxIdleConns = 4   // or a negative value to keep none, as before
```

Zero means the default. A negative value keeps no idle connections, matching
`database/sql`, and restores the old behavior for a deployment that needs it.

### What deliberately did not change

The maximum number of **open** connections stays unbounded. It depends on how many
replicas run against one database and how hard they are driven, which is a
service's decision. Services set it themselves, from configuration, when they
build the pool.

## SMTP delivery timeout

`smtp.ProdSender` now bounds every delivery. A send or a `Ping` that could hang
forever now fails after `smtp.DefaultTimeout` (30 seconds).

### Why the default is bounded rather than opt-in

`net/smtp` dials with no deadline and offers no cancellation. An SMTP host that
accepts the connection, then goes quiet, held the calling goroutine forever. A
security-group change does that, and so does a provider that throttles by
stalling.

Nothing reported it. The send is usually detached from its request, so delivery
survives request cancellation. The HTTP response is then written before the
goroutine blocks, so no latency signal, error rate or probe shows the stall. The
only symptom is a slow climb in memory. `Ping`, the readiness check that exists to
report a broken SMTP server, hung too, so the failure disabled the one signal an
operator would look at.

A timeout that must be opted into is eventually forgotten, and forgetting it is
silent. The bound therefore applies by default.

### Overriding it

If your SMTP provider legitimately takes longer than 30 seconds to accept a
message, set the new field:

```go
sender := &smtp.ProdSender{
    Addr:  cfg.Addr,
    Email: cfg.Email,
    // Connect, handshake, authentication and the message body share this budget.
    Timeout: 60 * time.Second,
}
```

A non-positive `Timeout` selects `DefaultTimeout`. No value means "unbounded",
since that is the state this release removes.

### Also new

`smtp.ErrNoAuthSupport` is returned when the server does not advertise the `AUTH`
extension. The standard library raised an unwrapped error there, and the sentinel
makes it matchable with `errors.Is`. Such a server was already rejected, so the
behavior stays the same.

### Under the hood

`ProdSender` now drives the SMTP exchange itself, because `smtp.SendMail` dials
internally and so cannot be bounded by the caller. The handshake transcribes what
`SendMail` does, in the same order: `STARTTLS` whenever the server offers it,
**before** any credential is sent, then `AUTH`. The set of servers accepted stays
the same.
