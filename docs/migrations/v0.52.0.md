# Migrating to v0.52.0

`sentryf` gives each event up to `sentryf.SendTimeout`, 2 minutes, to reach Sentry. sentry-go's own
transport dropped an event after 30 seconds. A process that starts before its network, such as a
fresh Cloud Run instance waiting for Cloud NAT, now sends its first events late instead of losing
them.

## Do I need to act?

**A job does.** Its `main` flushes with a timeout above `sentryf.SendTimeout`. A shorter flush can
end the process while an event still waits for the network:

```go
// SentryJobFlushTimeout outlasts sentryf.SendTimeout, so an event sent before the network came up
// still leaves.
const SentryJobFlushTimeout = sentryf.SendTimeout + time.Minute

defer sentryf.Flush(config.SentryJobFlushTimeout)
```

**A server does not.** It sends its events in the background while it runs, and its flush at exit
stays inside its platform's shutdown grace period.

A `Config.Transport` set by the caller keeps its own timeout.
